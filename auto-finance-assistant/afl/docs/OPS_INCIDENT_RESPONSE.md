# 运维管理制度与应急响应预案

> auto-finance-assistant v2.9.2  
> 生效日期：2026-07-27

---

## 一、运维管理制度

### 1.1 角色与职责

| 角色 | 职责 | 权限 |
|------|------|------|
| 系统管理员 | 系统部署、配置、监控 | 服务启停、配置修改 |
| 知识库管理员 | FAQ/文档维护 | FAQ/文档 CRUD |
| 数据安全负责人 | 合规监督、审计审查 | 审计日志查询、数据清理 |
| 模型安全负责人 | 内容安全策略、模型版本 | Guard/Compliance 规则调整 |

### 1.2 日常运维

#### 启动与停止

```bash
# 启动
.\start.ps1                                    # 前台启动（调试）
.\auto-finance-assistant.exe -config config.yaml run  # 直接启动

# 停止
.\stop.ps1                                     # 停止所有进程

# Windows 服务模式
.\scripts/install-service.ps1                  # 安装为服务
.\scripts/uninstall-service.ps1                # 卸载服务
```

#### 健康检查

```bash
# API 健康检查
curl http://127.0.0.1:8080/api/health

# 系统指标
curl -H "X-Admin-Password: xxx" http://127.0.0.1:8080/api/metrics

# 审计日志
curl -H "X-Admin-Password: xxx" http://127.0.0.1:8080/api/audit/logs
```

#### 数据备份

```bash
# 手动备份
curl -X POST -H "X-Admin-Password: xxx" http://127.0.0.1:8080/api/system/backup

# 备份保留：最近 7 份自动滚动
# 备份位置：data/backups/
```

### 1.3 模型版本管理

#### 模型更新流程

1. **评估必要性**：新模型版本是否修复安全漏洞或提升合规能力
2. **测试验证**：在测试环境运行 `eval.exe`，合格率≥90% 方可上线
3. **计算哈希**：`sha256sum new-model.gguf`，记录到《仅推理承诺书》
4. **变更报备**：如已取得备案，模型版本变更需向网信部门报备
5. **灰度切换**：先在备用实例部署，验证无误后切换
6. **回滚预案**：保留旧模型权重，可快速回滚

#### 知识库更新

1. 文档上传：管理后台 → 知识库 → 上传文档
2. 发布生效：上传后需"发布"才对客服可见
3. 向量化：发布后点"向量化"启用 RAG 检索
4. 审计记录：所有文档操作自动记录到 audit_logs

### 1.4 日志管理

| 日志类型 | 位置 | 保留期 | 轮转策略 |
|----------|------|--------|---------|
| 应用日志 | `data/logs/app.log` | 180 天 | 20MB 轮转，保留 7 个归档 |
| 审计日志 | SQLite `audit_logs` 表 | 90 天 | TTL 自动清理 |
| 审计日志（归档） | 数据库 | 永久（备份） | 每日备份 |

#### 日志审查

- **频率**：每周一次
- **重点**：auth.failed（认证失败）、compliance.refuse（合规拒答）、error 类操作
- **工具**：`GET /api/audit/logs?action=auth.failed`

### 1.5 访问控制管理

- 管理员密码存储于 `config.yaml`，**不得提交到代码仓库**
- 密码应至少 16 位，包含大小写字母+数字+特殊字符
- 密码每 90 天更换一次
- 密码更换需记录审计日志

## 二、应急响应预案

### 2.1 事件分级

| 级别 | 定义 | 响应时间 | 处理人 |
|------|------|---------|--------|
| P0 严重 | 系统生成违法有害内容被传播 | 立即 | 模型安全负责人 + 数据安全负责人 |
| P1 高危 | 系统被成功注入/越狱 | 15分钟 | 系统管理员 |
| P2 中危 | 服务不可用 / 性能严重下降 | 1小时 | 系统管理员 |
| P3 低危 | 个别功能异常 | 4小时 | 值班运维 |

### 2.2 P0 应急流程：违法有害内容

```
发现系统生成违法有害内容
  ↓ (立即)
1. 紧急关停服务
   .\stop.ps1
   # 或：taskkill /F /IM auto-finance-assistant.exe
  ↓
2. 保留证据
   - 导出审计日志（audit_logs 表）
   - 导出对话记录（messages 表）
   - 截图系统状态
   - 保存应用日志
  ↓
3. 分析根因
   - 检查 Guard 是否被绕过
   - 检查 Compliance 是否遗漏
   - 检查模型输出是否异常
  ↓
4. 修复并加固
   - 补充 Guard 关键词
   - 更新 Compliance 规则
   - 必要时回滚模型版本
  ↓
5. 验证后恢复
   - 运行 eval.exe 确认合格率≥90%
   - 灰度恢复服务
  ↓
6. 事件报告
   - 24小时内向网信部门报告（如涉及公众）
   - 内部留存事件记录≥6个月
```

### 2.3 P1 应急流程：注入/越狱攻击

```
发现注入攻击成功（系统输出了不当内容但未被拦截）
  ↓
1. 立即分析攻击 payload
   - 从审计日志提取攻击输入
   - 复现攻击路径
  ↓
2. 紧急补丁
   - 在 injectionPatterns 添加攻击特征
   - 重新构建并部署
  ↓
3. 验证
   - 用攻击 payload 重测，确认被拦截
   - 运行 eval.exe 回归测试
  ↓
4. 记录
   - 审计日志记录事件
   - 评估是否需上报网信部门
```

### 2.4 P2 应急流程：服务不可用

```
服务无法访问
  ↓
1. 检查进程
   Get-Process auto-finance-assistant
   Get-Process llama-server / ollama
  ↓
2. 检查日志
   # 最后 50 行日志
   Get-Content data/logs/app.log -Tail 50
  ↓
3. 常见原因
   - 模型未加载 → 重启 llama-server
   - 端口冲突 → 检查 8080/8081/8082 端口
   - 数据库锁 → 检查 WAL 文件
   - 内存不足 → 检查 RAM/VRAM
  ↓
4. 恢复
   .\stop.ps1
   .\start.ps1
  ↓
5. 验证
   curl http://127.0.0.1:8080/api/health
```

### 2.5 数据泄露应急

```
发现数据泄露（如对话记录被未授权访问）
  ↓
1. 立即切断访问
   - 关闭服务
   - 修改管理员密码
   - 检查防火墙规则
  ↓
2. 评估泄露范围
   - 查询审计日志：auth.failed + 数据访问记录
   - 确定泄露的数据量和类型
  ↓
3. 通知
   - 72小时内通知受影响用户（PIPL 要求）
   - 向网信部门报告（如涉及个人信息）
  ↓
4. 修复
   - 加固访问控制
   - 审查权限配置
   - 补充安全措施
```

## 三、定期评估制度

### 3.1 月度评估

| 评估项 | 方法 | 标准 |
|--------|------|------|
| 内容安全合格率 | `eval.exe` 评测 | ≥90% |
| Guard 拦截有效性 | 审计日志分析 | 注入拦截率 100% |
| 审计日志完整性 | 抽查管理操作 | 100% 有记录 |
| 服务可用性 | 监控数据 | ≥99% |

### 3.2 季度评估

| 评估项 | 方法 |
|--------|------|
| 安全漏洞扫描 | 渗透测试 |
| 合规自评估 | 对标 GB/T 45654 |
| 用户反馈分析 | 反馈表统计 |
| 知识库质量 | 抽检问答准确性 |

### 3.3 年度评估

| 评估项 | 方法 |
|--------|------|
| 全面安全评估 | 第三方测评机构 |
| 等保复测 | 公安部测评机构 |
| 备案更新 | 网信部门 |
| 数据销毁验证 | 抽查 TTL 清理记录 |

| 事件类型 | 上报对象 | 时限 |
|----------|---------|------|
| 违法有害内容 | 网信部门 + 公安 | 24小时 |
| 个人信息泄露 | 网信部门 + 当事人 | 72小时 |
