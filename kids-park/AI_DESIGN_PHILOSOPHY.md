# KidsPark · AI 协作设计哲学

> 综合自《Pi Agent 框架评测》与《Godot + AI 全流程实操》两文的核心洞察，指导本项目的 AI 协作决策。

## 一、Pi 的"减法哲学"对本项目的启发

### 核心命题
> **"看一个什么都做了的框架，你只能学到他们做了什么。看一个刻意什么都不做的框架，你才能学到做一件事到底需要什么。"**

Pi 框架只有 4 个工具（read/write/edit/bash），却打赢了有 MCP/多 Agent 的竞品。这说明**大量"看似必需"的功能其实并非必需**。

### 对照 kids-park 的反思

kids-park 走的是**加法路线**（40 脚本、30+ 玩法）。这没错——游戏需要内容密度。但 Pi 的哲学提醒我们定期做**减法审计**：

#### 该砍的（死代码 / 无实际效果）
| 项目 | 问题 | 处理 |
|------|------|------|
| `EventBus.confetti_burst` 信号 | 声明但从未 emit，直接调 `Confetti.burst()` | 已知，待清理 |
| `EventBus.mission_*` 三个信号 | 声明但未接入 | 待清理或接入 |
| `GameState.mission_progress` | 字段存在但未使用 | 待清理或启用 |
| `_apply_tint()` | no-op stub，tint 参数算了但不用 | 实现或删除 |
| `_make_warm_lut()` | 定义但未调用（注释说保留） | 已注释说明 |

#### 该留的（有实际游戏效果）
所有"看起来复杂"但确有反馈的系统都该留：
- 连击系统（已修复为发放实际物品奖励）
- 宝箱（已修复过滤逻辑）
- 成就（已接入 toast + 音效 + 全屏特效）

**减法准则**：每加一个功能，问自己"如果删掉它，玩家会注意到吗？" 答案为否 → 考虑删。

## 二、Godot 为何是 AI 时代最优引擎（结构性匹配）

### 三大匹配点（本项目已验证）

#### 1. 节点-场景树 ≈ AI 最擅长的数据结构
- Godot 的节点树是**可递归遍历的树**，层级明确
- `.tscn` 是**纯文本**，AI 可直接读写
- 对比：Unity Prefab 是二进制，AI 必须 API 间接操作

**本项目实证**：`Main.gd` 运行时构建整个场景树（200+ 行），AI 能完整理解每个节点的父子关系。

#### 2. GDScript 降低 AI 出错率
- 无 C# 的命名空间/生命周期签名胶水代码
- 语法接近 Python，AI 出错面小
- **本项目实证**：绝大多数 GDScript 首次编译即通过（除 CSG 属性名误用等小错）

#### 3. 命令行友好（headless 验证闭环）
```bash
# 编译验证 → 测试 → 截图 → 打包，全命令行无 GUI
Godot.exe --headless --quit-after 60              # 编译
KIDS_PARK_E2E=1 Godot.exe --headless              # 测试
PARK_SCREENSHOT=1 Godot.exe                       # 截图
Godot.exe --headless --export-debug "Android Debug"  # 打包
```

### 本项目已形成的 AI 验证闭环
```
AI 写代码 → headless 编译验证 → E2E 测试 → 截图视觉验证 → APK 打包
    ↑                                                              |
    └──────────── 失败则 AI 修复 ←─────────────────────────────────┘
```
这个闭环是**无需人工介入**的，这正是 Godot 命令行能力的价值。

## 三、上下文窗口是最稀缺资源

### Pi 的启示
Pi 的系统提示词只有 ~90 词（Claude Code 是数万字）。这直接决定 Agent 能"看到"多少你的代码。

### 对 AI 协作的实操指导
1. **AGENTS.md 要精准，不要冗长** —— 但要覆盖：架构、命名规范、决策树、已知坑
2. **分模块沟通** —— 不要一次把 40 个文件都喂给 AI，按模块（autoload/world/ui/player）分批
3. **提供代码示例** —— "用 `ModelFactory.get_material()` 而非 `StandardMaterial3D.new()`" 比"缓存材质"更有效

### 本项目 AGENTS.md 的设计
采用**分层结构**：
- 上半部：人类阅读的玩法清单 + 架构图
- 下半部：AI 读取的 CLAUDE.md 等价规范（编码规范 + 检查清单）

## 四、AI 工具链分层使用策略

### 本项目实际使用的层级
```
┌─────────────────────────────────────────┐
│  Claude Code（AI 编码层）← 主要使用      │
│  - 写 GDScript                          │
│  - 读/改文件                            │
│  - 运行 bash 命令验证                   │
├─────────────────────────────────────────┤
│  Godot 命令行（验证层）← 主要使用        │
│  - --headless --quit-after 编译         │
│  - --export-debug 打包                  │
├─────────────────────────────────────────┤
│  Godot MCP（编辑器操控层）← 未使用      │
│  - 可视化验证                           │
│  - 批量建节点                           │
├─────────────────────────────────────────┤
│  AI 素材生成（图像层）← 未使用          │
│  - 贴图/图标生成                        │
│  - 见 ASSET_PIPELINE.md                 │
├─────────────────────────────────────────┤
│  游戏内 AI（NPC 对话）← 未使用          │
│  - NobodyWho 本地 LLM                   │
└─────────────────────────────────────────┘
```

### 为什么当前不用 MCP？
- **稳定性**：MCP 连接断开常见，命令行更可靠
- **上下文成本**：MCP 工具描述占大量 token
- **本项目规模**：40 脚本通过文件读写已够用

### 何时引入 MCP？
- 当需要**视觉验证**（截图比对布局）
- 当需要**批量操作**（一句话建 50 个收集物节点）
- 当项目超过 100 脚本、纯文本导航变慢时

## 五、定期审计清单（借鉴 Pi 的"不做什么"）

每个开发阶段结束时，过一遍这个清单：

### 死代码检查
- [ ] 有声明但从未 emit 的信号？
- [ ] 有定义但从未调用的函数？
- [ ] 有 import 但从未使用的 preload？
- [ ] 有字段写入了但从未读取？

### 效果检查（Pi 式质问）
- [ ] 这个功能删了，玩家会注意到吗？
- [ ] 这个 UI 元素有人看吗？
- [ ] 这个音效有人听得见吗？
- [ ] 这个参数调了有视觉差异吗？

### 复杂度检查
- [ ] 有没有可以用一个系统替代的两个相似系统？
- [ ] 有没有过度抽象（接口只有一个实现）？
- [ ] 有没有可以合并的重复代码？

### 性能检查
- [ ] `_process` / `_physics_process` 里有 `new` / `load` / group 查找？
- [ ] 有未缓存的重引用？
- [ ] SubViewport 是否 `UPDATE_ALWAYS`（应该降频）？

## 六、文档维护原则

1. **AGENTS.md 是单一真相源** —— 玩法清单、架构图、规范都在这里
2. **新增功能必须同步更新 AGENTS.md** —— 否则下次 AI 协作会基于过期信息
3. **踩坑即记录** —— 每个编译错误/逻辑 bug 修完后，把教训写进规范（如 CSGCylinder 无 top_radius）
4. **文档也要做减法** —— 过时的内容及时删，不要堆砌成"历史考古文档"
